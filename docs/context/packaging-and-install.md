# Packaging and Install — the Widget Lifecycle

From "the version was bumped" to "the user's panel shows the new build": one authored
version, one idempotent installer, one derived update manifest. This doc is the rule; the two
widgets are the evidence.

## Version is authored exactly once

`KPlugin.Version` in the package's `metadata.json` is the **single source of version truth**.
Nothing downstream of it may be typed by hand — a second hand-typed version is a second truth
and it drifts. Docker derives everything else from that one file:

```
package/io.github.daver-ui.dockerstatus/metadata.json   # the only authored version
        │
        ├─ site/latest.json        (regenerated by .github/scripts/sync-manifest.mjs)
        └─ dist/latest.json        (the same bytes, uploaded for GitHub Pages to serve)
```

The version shape is one to three dot-separated numeric segments, no leading zeros
(`1`, `0.4`, `0.5.0`). Comparison is numeric, segment by segment — `0.10 > 0.9`, never a
lexicographic string compare. A segment that is not that shape is refused everywhere at once,
so a version cannot be half-parsed.

## The idempotent installer idiom

Both installers are Bash with the same shape. It is the shape that matters, not the widget.

- **`set -euo pipefail`** — a partial install aborts loudly rather than half-finishing.
- **Paths derived from the script's own directory**, so the installer behaves identically
  from any working directory:

  ```sh
  SCRIPT_DIR="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)"
  ```

  A path resolved against the caller's cwd is a bug, because the documented usage is
  `./install.sh` from the repo root.
- **`--install` vs `--upgrade` decided by a probe**, never by the caller:

  ```sh
  if kpackagetool6 --type Plasma/Applet --show "$ID" >/dev/null 2>&1; then
      kpackagetool6 --type Plasma/Applet --upgrade "$PKG"
  else
      kpackagetool6 --type Plasma/Applet --install "$PKG"
  fi
  ```

- **Plain-copy fallback** when `kpackagetool6` is unavailable: `rm -rf` then copy into
  `${XDG_DATA_HOME:-$HOME/.local/share}/plasma/plasmoids/<id>`.
- **Removal mirrors installation exactly.** A removal that disagrees with its install path is
  the classic silent leak.

Docker's installer is a `case` dispatcher over six commands — `install`, `uninstall`,
`install-polkit`, `remove-polkit`, `test`, `status`
([install.sh](../../widgets/docker-status-widget/install.sh)). The widget install is
unprivileged and reversible; the polkit rule is a **separate** command that needs `sudo`, so a
system-wide privilege grant never happens implicitly. Tuya's installer additionally creates a
virtualenv, seeds a `0600` config it never overwrites, installs a desktop launcher, and then
installs the applet
([install.sh](../../widgets/tuya-bulb-widget/install.sh)).

## Stage-then-install

**Never install an unrendered template, and never rewrite a template in place.** When the
package carries an install-time value (tuya bakes the absolute CLI path into the kcfg
default), the installer renders the template into a staging directory inside the gitignored
build tree first, then installs *from the staging directory*:

```
plasmoid/<id>/ (template, committed)  ──render──▶  plasmoid/build/<id>/ (staged)  ──▶ kpackagetool6
```

`render-plasmoid.sh` rewrites the whole target from the template (`rm -rf` then `cp -r`), so a
stale file from a previous render cannot survive, and escapes XML first and sed second so an
install path containing `&`/`<`/`>` stays literal. A package with no install-time value
(docker) skips all of this — `package/<id>/` is the artifact. See
[plasmoid-anatomy](plasmoid-anatomy.md) for which shape to choose.

## kpackagetool6 vs plasmapkg2

Plasma 6 uses **`kpackagetool6`**. `plasmapkg2` belongs to the Plasma 4/5 era: it predates the
KPackage framework and the `metadata.json` layout, so it is obsolete here and neither author
widget references it. When `kpackagetool6` is missing, the fallback is a **plain directory
copy** into the plasmoid store, not an older packaging tool — that keeps the installer working
on a machine with no KDE development packages installed.

## The release site and the fixed update manifest

A widget can tell the user a newer release exists without a package repository: the author
publishes a **machine-readable manifest** on GitHub Pages, and the installed widget polls it.

- `.github/scripts/sync-manifest.mjs` reads `metadata.json` and writes `site/latest.json` in a
  fixed key order — `app`, `name`, `version`, `released`, `url` — where `version` is
  `KPlugin.Version`, `app`/`name`/`url` are derived, and `released` is a generation stamp.
  `--write` is write-if-diff; `--check` is read-only and exits non-zero on drift.
- The **Pages workflow** regenerates the manifest from `metadata.json` on every push to
  master and assembles the publishable site into `dist/` fresh — no generated file is ever
  committed back by CI
  ([pages.yml](../../widgets/docker-status-widget/.github/workflows/pages.yml)).
- The **CI gate** runs `sync-manifest.mjs --check` as a step, so a pull request that bumps
  `KPlugin.Version` fails until `site/latest.json` is regenerated alongside it.

The widget side is deliberately the opposite of a command-building exception: the check is
assembled **entirely from fixed constants**. It `cat`s its own installed `metadata.json`,
prints a marker line, then `curl -fsSL --max-time 5` fetches the manifest URL. One one-shot
yields both halves; the marker splits them. Every failure — no `curl`, a missing
`metadata.json`, offline, an unparseable manifest — collapses silently to "no update
available", because a check the user did not ask for must never nag.

### Why the manifest URL is a constant, not a setting

The widget polls **one fixed https URL** and opens **one fixed release-page URL**; both are
constants in the JS core, not configuration. The reason is the same one that keeps the
version path safe: if the URL were a setting, a misconfiguration could point the widget at
another host, and the widget would become an exfiltration surface. A constant cannot.

That makes **"keep the repo name and the Pages URL stable" a hard requirement**, not a
preference. The `github.io` path is derived from the repository name; **renaming the repo
changes the manifest URL and silently breaks the update check in every already-installed
widget**, with no error ever shown. Treat the repo name, the Pages URL, and the release asset
URL as immutable once published.

## Release checklist

Run by hand, in the widget's own repository, in order:

1. **Bump** `KPlugin.Version` in the package's `metadata.json`. Nowhere else.
2. **Regenerate the manifest** from that one file:
   `node .github/scripts/sync-manifest.mjs --write`.
3. **Commit** the version bump and the regenerated manifest together, then **tag** the release.
4. **Re-install** locally to verify the shipped bytes:
   `kpackagetool6 --type Plasma/Applet --upgrade <package-dir>` (or run the installer, which
   chooses install vs upgrade for you).
5. Add the widget through **Add Widgets…**, and restart plasmashell
   (`kquitapp6 plasmashell && kstart plasmashell`) if it does not appear.

## Known gaps

- **`plasmapkg2` is not exercised** — the claim that it is obsolete for Plasma 6 is stated
  from the tool's era, not measured against a running install.
- **Nothing verifies that plasmashell actually reloaded a widget after an upgrade.** The
  installer prints the restart reminder and trusts the user (recorded as accepted debt in the
  docker installer slice).
- **The plain-copy fallback bypasses KPackage metadata handling** and can leave a stale
  directory behind after an upgrade, because `kpackagetool6`'s bookkeeping is skipped.
- **No distribution packaging, no system-wide install, no version pinning** beyond what
  `kpackagetool6 --upgrade` decides.
